# 結合テスト（操作確認）

4つの API の応答と、受付画面での操作が待合室画面に反映されることを確認する。

## ローカルでの起動手順

1. Visual Studio で [WaitingRoom.slnx](../../WaitingRoom.slnx) を開く。
2. ソリューション エクスプローラーで `WaitingRoom.Web` を右クリックし、**「スタートアップ プロジェクトに設定」**を選ぶ。
3. 上部の構成で **`Debug`**、緑の再生ボタン横の起動プロファイルで **`https`** を選び、**`F5`** で起動する。
4. アプリがすでに動いていて、受付データを空にする必要がある場合は、**`Shift + F5`** で停止し、**`F5`** で起動し直す。アプリを停止すると、メモリに保存していた受付データが初期化される。

## API の確認（ローカル）

1. [ローカルでの起動手順](#ローカルでの起動手順)に沿ってアプリを起動し、Visual Studio で [WaitingRoom.Web.http](../../WaitingRoom.Web.http) を開く。
2. 表の手順にある `GET` または `POST` と URL の末尾（例 `/api/tickets`）が一致するリクエストを探す。案内完了の `POST /api/tickets/{number}/complete` では、URL の受付番号を表で指定された番号に置き換える。
3. リクエストの上にある **「要求の送信」** を押し、応答欄で結果を見る。

リクエストを続けて送るときは、前の応答が表示されてから次のリクエストを送信する。

| 区分 | 確認項目 | 前提条件 | 手順 | 期待結果 | 確認結果 |

| 正常系 | 発行した番号の画面反映 | ローカルで `WaitingRoom.Web` が `https` で起動し、PC でブラウザーを使える。 | 1. ローカルアプリを起動し直す。<br>2. 受付画面を開く。<br>3. 待合室画面を別のタブで開く。<br>4. 受付画面で「受付番号を発行」を2回押す。1回目の反映を待ってから2回目を押す。<br>5. 待合室画面で「更新」を1回押す。 | 手順4で受付画面に2件が発行順に並ぶ。<br>手順5で待合室画面の待機人数が2人になる。 |  |

## 公開後の動作確認（Azure）

確認対象のバージョンが Azure App Service にまだ発行されていない場合は、発行する。公開先の受付画面は `/Pages/Reception`、待合室画面は `/Pages/WaitingRoom` を開く。

受付データを初期化するときは、Azure ポータルで対象の App Service を開き、**「概要」→「再起動」** を押す。再起動が終わり、ブラウザーで画面が開けるようになってから次の操作に進む。

| 区分 | 確認項目 | 前提条件 | 手順 | 期待結果 | 確認結果 |
|---|---|---|---|---|---|
| 正常系 | 公開先で番号発行から案内完了まで確認する | 確認対象のバージョンが Azure App Service に発行済みで、PC とスマートフォンから接続できる。 | 1. ほかの人が操作していないことを確認する。<br>2. Azure ポータルで対象の App Service を再起動する。<br>3. PC で公開先の受付画面を開く。<br>4. スマートフォンで同じ公開先の待合室画面を開く。<br>5. PC で「受付番号を発行」を1回押す。<br>6. スマートフォンの待合室画面で「更新」を1回押す。<br>7. PC で「次を呼ぶ」を1回押す。<br>8. スマートフォンの待合室画面で「更新」を1回押す。<br>9. PC で「案内完了」を1回押す。<br>10. スマートフォンの待合室画面で「更新」を1回押す。 | 手順4で待機人数は0人。<br>手順6で待機人数が1人になる。<br>手順8で両画面に発行した番号が表示され、待機人数が0人になる。<br>手順10で両画面から呼び出し中の番号が消え、待機人数は0人のまま。 |  |
