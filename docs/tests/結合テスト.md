# 結合テスト（操作確認）

4つの API の応答と、受付画面での操作が待合室画面に反映されることを確認する。

## ローカルでの起動手順

1. Visual Studio で [WaitingRoom.slnx](../../WaitingRoom.slnx) を開く。
2. ソリューション エクスプローラーで `WaitingRoom.Web` を右クリックし、**「スタートアップ プロジェクトに設定」**を選ぶ。
3. 上部の構成で **`Debug`**、緑の再生ボタン横の起動プロファイルで **`https`** を選び、**`F5`** で起動する。
4. アプリがすでに動いていて、受付データを空にする必要がある場合は、**`Shift + F5`** で停止し、**`F5`** で起動し直す。アプリを停止すると、メモリに保存していた受付データが初期化される。

## API の確認（ローカル）

1. [ローカルでの起動手順](#ローカルでの起動手順)に沿ってアプリを起動し、Visual Studio で [WaitingRoom.Web.http](../../WaitingRoom.Web.http) を開く。
2. 表の手順にある `GET` または `POST` と URL の末尾（例 `/api/tickets`）が一致するリクエストを探す。案内完了の `POST /api/tickets/{number}/complete` では、URL の受付番号を表で指定された番号に置き換える。
3. リクエストの上にある **「要求の送信」** を押し、応答欄で結果を見る。

前提条件の準備も同じファイルで行う。番号発行には `POST /api/tickets`、次の呼び出しには `POST /api/queue/call-next` を使う。

前提条件に「まだ番号を発行していない」とある項目は、共通の起動手順に沿って受付データが空の状態にしてから始める。

| 区分 | 確認項目 | 前提条件 | 手順 | 期待結果 | 確認結果 |
|---|---|---|---|---|---|
| 正常系 | 番号発行 API の応答 | ローカルでアプリを起動した直後で、まだ番号を発行していない。 | `POST /api/tickets` を1回送信する。 | `201 Created` と `{"number":"A001"}` が返る。 |  |
| 正常系 | 受付状況 API の応答 | 2件発行し、1件目を呼び出しておく。 | `GET /api/queue` を送信する。 | `200 OK` が返る。`callingNumber` は1件目、`waitingNumbers` には2件目だけが入る。 |  |
| 正常系 | 次の番号を呼び出す API の応答 | 呼び出し中の番号がなく、2件が待機している。 | `POST /api/queue/call-next` を送信し、続けて `GET /api/queue` を送信する。 | `200 OK` と1件目の番号が返る。1件目が呼び出し中になり、2件目だけが待機列に残る。 |  |
| 正常系 | 案内完了 API の応答 | 1件目が呼び出し中で、2件目が待機している。 | `POST /api/tickets/{number}/complete` に1件目の番号を指定して送信し、続けて `GET /api/queue` を送信する。 | `204 No Content` が返る。`callingNumber` は `null` になり、2件目だけが待機列に残る。 |  |
| 異常系 | 待機列が空のときの呼び出し | 呼び出し中の番号がなく、待機列が空。 | `POST /api/queue/call-next` を送信し、続けて `GET /api/queue` を送信する。 | `409 Conflict` が返り、受付状況は空のまま。 |  |
| 異常系 | 呼び出し中にもう一度呼び出す | 1件目が呼び出し中で、2件目が待機している。 | `POST /api/queue/call-next` を送信し、続けて `GET /api/queue` を送信する。 | `409 Conflict` が返り、呼び出し中の番号と待機列は変わらない。 |  |
| 異常系 | 未発行の番号の案内完了 | ローカルでアプリを起動した直後で、まだ番号を発行していない。 | `POST /api/tickets/{number}/complete` に未発行の `A001` を指定して送信する。 | `404 Not Found` が返る。 |  |
| 異常系 | 待機中の番号の案内完了 | 1件目が呼び出し中で、2件目が待機している。 | `POST /api/tickets/{number}/complete` に2件目の番号を指定して送信する。 | `409 Conflict` が返る。 |  |

## 画面の操作確認（ローカル）

1. [ローカルでの起動手順](#ローカルでの起動手順)に沿ってアプリを起動し、受付データが空の状態でテストを始める。
2. PC のブラウザーで受付画面（`https://localhost:7136/Pages/Reception`）と待合室画面（`https://localhost:7136/Pages/WaitingRoom`）を別々のタブで開く。

番号発行から呼び出し、案内完了まで続けて確認するときは、その場で発行した番号を引き継ぐ。同時呼び出しを続けて試す場合は、呼び出し中の番号を案内完了にし、新しく番号を2件発行してから、受付画面を2つのウィンドウで開く。

| 区分 | 確認項目 | 前提条件 | 手順 | 期待結果 | 確認結果 |
|---|---|---|---|---|---|
| 正常系 | 画面を開いたときの表示 | 呼び出し中の番号がなく、待機列が空。 | 受付画面と待合室画面を開く。 | 両画面に「呼び出し中の番号はありません」と表示される。受付画面の待機列は空で「次を呼ぶ」は押せず、待合室画面の待機人数は0人。 |  |
| 正常系 | 発行した番号の画面反映 | 呼び出し中の番号がなく、待機列が空。 | 受付画面で「受付番号を発行」を2回押す。1回目の反映を待ってから2回目を押し、待合室画面で「更新」を押す。 | 受付画面に2件が発行順に並び、待合室画面の待機人数が2人になる。 |  |
| 正常系 | 呼び出しの画面反映 | 呼び出し中の番号がなく、2件が待機している。 | 受付画面で「次を呼ぶ」を1回押し、待合室画面で「更新」を押す。 | 両画面で先頭の番号が呼び出し中になり、待合室画面の待機人数は1人になる。受付画面の「次を呼ぶ」は押せない。 |  |
| 正常系 | 案内完了と次の呼び出しの画面反映 | 1件目が呼び出し中で、2件目だけが待機している。 | ①「案内完了」を押し、待合室画面で「更新」を押す。②「次を呼ぶ」を押し、待合室画面で再度「更新」を押す。 | ①両画面で呼び出し中の番号がなくなり、待機人数は1人のまま。②両画面で2件目が呼び出し中になり、待機人数は0人になる。 |  |
| 異常系 | 2つの受付画面からの同時呼び出し | 呼び出し中の番号がなく、2件が待機している。受付画面を同じ環境で2つ開く。 | 2つの受付画面で「次を呼ぶ」をほぼ同時に押し、操作後に両画面を再読み込みする。 | 先頭の1件だけが呼び出し中になり、2件目は待機列に残る。 |  |

## 公開後の動作確認（Azure）

1. 確認対象のバージョンが Azure App Service にまだ発行されていない場合は、発行する。発行済みの場合は手順2に進む。
2. ほかの人が操作していないことを確認し、Azure ポータルで対象の App Service を開き、**「概要」→「再起動」** を押す。再起動すると、メモリに保存されている受付データが初期化される。
3. 同じ公開先の受付画面（`/Pages/Reception`）を PC で、待合室画面（`/Pages/WaitingRoom`）をスマートフォンで開く。

| 区分 | 確認項目 | 前提条件 | 手順 | 期待結果 | 確認結果 |
|---|---|---|---|---|---|
| 正常系 | 公開先で番号発行から案内完了まで確認する | 呼び出し中の番号がなく、待合室画面の待機人数が0人。 | PC の受付画面で①「受付番号を発行」、②「次を呼ぶ」、③「案内完了」を1回ずつ押す。各操作の直後にスマートフォンの待合室画面で「更新」を押して確認する。 | ①待機人数が1人になる。②両画面で発行した番号が呼び出し中になり、待機人数が0人になる。③両画面で呼び出し中の番号がなくなり、待機人数は0人のまま。 |  |
